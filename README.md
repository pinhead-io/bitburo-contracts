# bitburo-contracts

Bitburo's immutable `Rebalancer` contract on Base mainnet, plus the two external keepers.

The user gives the contract an ERC-20 mandate (allowance) for EURC and cbBTC and sets their own settings. The contract rebalances from the user's wallet towards the chosen allocation; the money stays in the wallet. Bitburo has no key with which it can touch settings or funds; the treasury's only power is the one-time kill switch `retire()` (see [Retiring the contract](#retiring-the-contract)). Design and decisions: see the handover (private artifact, held by Arjan).

## Contract interface

| Function | What |
|---|---|
| `setParams(Params)` | Set or change your own settings. Bounds: `bandBps` 125–9999 (`MIN_BAND_BPS`, see below), `minTradeEurc` ≥ `MIN_TRADE_FLOOR` (20 EURC), `maxCorrectionBps` 10–10000, `maxSlippageBps` 60–100, `interval` ≥ 1 hour. Aborts a running round (see [Chunks](#large-corrections-in-chunks)). After `retire` only with `active = false` (revoking the mandate); otherwise `ContractRetired`. |
| `isDue(owner) → (bool, int256)` | Would `execute` do something now, and how much EURC (+ buy, − sell)? The amount is what `execute` would actually trade now, so already capped by balance, allowance and the block window (for sells, the cbBTC to be sold at the Chainlink price). During a round that is the next chunk. Never reverts; a pool that already wrote an observation in this block, or too little room in the block window, gives `(false, 0)`. After `retire` always `(false, 0)`. |
| `owners(offset, limit) → address[]` / `ownerCount()` | A page of all registered owners (including inactive ones); the count. Never reverts, not even with `limit = type(uint256).max`. |
| `dueOwners(offset, limit) → address[]` | One call per page: the owners that are due now, same rules as `isDue`. The app keeper uses this; the script in `keeper/` first filters the registry on balance and allowance and then asks `isDue` per candidate (lead 9). All owners in the list share the same block window: after one run in a block there is usually no room left for the rest. If a pool already has an observation in this block, the list is empty. Never reverts, not even with a large `limit`. After `retire` always empty. Gas: the run size (tick and liquidity state) is computed once per direction per page (review I-2); a page of 50 due owners (25 buy, 25 sell, cold storage) costs 1,243,658 gas at Base block 51,390,800, was 1,673,109 (`test_fork_dueOwnersGasPerPage`). Keep an eye on the node's gas limit for `eth_call` with large pages. |
| `execute(owner, rewardTo)` | One rebalance step (a whole correction or one chunk of it); anyone may call this. `rewardTo` = the contract itself counts as `address(0)`. Reverts before the swap with `PoolTouchedThisBlock(pool)` (selector `0x817a53db`) if a pool already wrote an oracle observation in this block, with `BlockMoveExceeded(pool)` (`0x66356d6d`) if there is too little room or liquidity or the price after the swap lies outside the block window (both temporary: try again next block), with `NoOutput` if the buy would yield 0 cbBTC, and with `ContractRetired` after `retire`. |
| `lastExecutedAt(owner) → uint64` | Time of the last successful run, including a chunk. A new round can only start `interval` after that. |
| `rounds(owner) → (bool isBuy, uint128 remainingEurc)` | Running round: direction and what is left of the budget. `remainingEurc = 0` = no round. |
| `sweep(token)` | Sends a leftover balance to the treasury (tokens sent by accident, or fee left behind by a failed treasury transfer). Permissionless. Also works after `retire`. |
| `retire()` | One-time, irreversible kill switch. Only `TREASURY`; a second call reverts with `AlreadyRetired`. Sets `retired = true` and emits `Retired()`. Can do nothing with funds or settings. |
| `retired() → bool` | Is the contract retired? |
| `quote()` / `spot()` / `quoteChecked()` | Feed price; pool spot; feed price with the spot check of `execute`. All three in EURC base units per cbBTC. |

Constants: `FEE_BPS` 25, `KEEPER_REWARD_EURC` 0.05 EURC (at most half the fee of a run), `MIN_TRADE_FLOOR` 20 EURC (fee of the smallest run 0.05 EURC: half to the caller, half to the treasury), `MIN_CORRECTION_BPS` 10, `MIN_BAND_BPS` 125 (= `FEE_BPS` + `MAX_SLIPPAGE_BPS`: a run only happens at a deviation larger than the most a run can cost, so that a permissionless caller cannot make a wallet trade repeatedly on small price movements without the allocation really improving, and a full correction finishes in one run; math audit `audit/2026-09-15/details/math.md` I-01), `MIN_SLIPPAGE_BPS` 60 / `MAX_SLIPPAGE_BPS` 100, `MAX_SPOT_DEVIATION_BPS` 50, `MAX_AGE_CBBTC` 1500 s, `MAX_AGE_EURC` 4500 s (hourly feed `0x9867…01e0`), `FEED_DECIMALS` 8 (enforced in the constructor), `POOL_FEE` 500 (0.05%), `TICK_SPACING` 10, `MAX_BLOCK_MOVE_BPS` 6, `SIZING_BPS` 7500 (75%), `CHUNK_INTERVAL` 10 minutes.

The constructor checks the token decimals (EURC 6, cbBTC 8, USDC 6, otherwise `UnexpectedTokenDecimals`; review I-4): the units, `MIN_TRADE_FLOOR` and the reward are fixed amounts in base units. It also checks the two pools: tokens (`UnexpectedPoolTokens`), fee tier equal to `POOL_FEE` (`UnexpectedPoolFee`), tickSpacing equal to `TICK_SPACING` (`UnexpectedTickSpacing`; the run sizing relies on it, see below), and that they are exactly the pools that `getPool(…, 500)` returns on the router's factory (`ROUTER.factory()`, otherwise `PoolNotFromRouterFactory`). This guarantees that the spot check guards the pools the swap goes through (audit lead 1). On Base, SwapRouter02 `0x2626…e481` returns factory `0x3312…FDfD`, and for both pairs at fee 500 that factory returns the pools from `script/Deploy.s.sol` (checked with `cast call` on 16 September 2026; both pools and `feeAmountTickSpacing(500)` of that factory return tickSpacing 10).

### Fee, reward and maximum loss per run

The fee is 25 bps of the EURC leg of each run: for buys over the gross amount, for sells over the higher of the amount actually received and the expected proceeds at the Chainlink price, and never more than the amount received. This way a sell at the floor of 20 EURC still yields a fee of 0.05 EURC after pool fees and slippage (audit L-B). Of that, `min(0.05 EURC, fee / 2)` goes to `rewardTo`, the rest to the treasury. Half as the cap (self-audit 2026-09-17, L-D): otherwise, for a run at the floor, the whole fee went to the reward, and an owner calling `execute` for themselves with `rewardTo` = themselves traded without a fee. Now the treasury receives at least half of every run. A chunk of a round is an ordinary run: fee and reward are deducted there too, and every chunk is also at least `MIN_TRADE_FLOOR`. Both transfers are non-reverting: if the reward fails (for example a blacklisted `rewardTo`), the whole fee goes to the treasury; if the treasury transfer fails, that part stays in the contract (`FeeRetained(amount)`) and `sweep(EURC)` collects it later. The rebalance itself therefore never breaks on the fee recipient.

**The maximum loss per run relative to the Chainlink price is `FEE_BPS + maxSlippageBps`** (0.85–1.25%). The spot check below is not an additional upper bound on that. **The cap (`maxCorrectionBps`) applies per round, not per day**: with an `interval` of 1 hour and a cap of 10%, a wallet can move up to 24 × 10% per day. A round can proceed in chunks, but together never above its budget (see [Chunks](#large-corrections-in-chunks)). Anyone who wants a daily cap sets `interval` to a day.

**Changing or revoking is not atomic (audit lead 7).** Base builds every block in Flashblocks of 200 ms and orders by priority fee within a Flashblock; the arrival time determines which Flashblock a transaction lands in ([docs.base.org, block building](https://docs.base.org/base-chain/network-information/block-building), read on 16 September 2026). So it is not first-come-first-served, as the AI audit assumed. Anyone who sees a `setParams` or `approve(0)` before it is in a Flashblock can put an `execute` in front of it with a higher tip. That run then happens on the old settings, with the same bounds as any other run:
- **At most one run.** After that `interval` (≥ 1 hour) applies, or within a round `CHUNK_INTERVAL`; `setParams` aborts a running round, and after `approve(0)` on the input token there is no next run.
- **Bounded.** The block window bounds the size, and the maximum loss relative to Chainlink remains `FEE_BPS + maxSlippageBps` of the old settings, so within the mandate the user had still given at that point.
- **No profit without an LP share.** The caller only gets the keeper reward; a push within the tick yields nothing without own liquidity, and with a large LP share at most the bounded residual profit from [Sandwich protection](#sandwich-protection-audit-m-1-l-3).

A keeper could have made the same run without malicious intent, at any moment the owner was due. Base's RPC offers no `txpool` methods (`mainnet.base.org` returns "this request method is not supported"), but anyone sending through a third party trusts that party. If you want to be sure there are no more runs, send `approve(0)` first.

### Sandwich protection (audit M-1, L-3)

`execute` is permissionless, so the caller can push the pool, call `execute` and push back in one transaction. Three layers keep that unprofitable.

**1. Block check and block window per pool.** A run only happens if neither pool has already written an oracle observation in the same block: `observations[slot0.observationIndex].blockTimestamp` must not equal the block's timestamp. Otherwise `execute` reverts before the swap with `PoolTouchedThisBlock(pool)` and `isDue` and `dueOwners` report nothing. On top of that, the price before and after the swap must lie within `MAX_BLOCK_MOVE_BPS` (6 bp) of the tick at the start of the block, including the run's own swap; otherwise `BlockMoveExceeded(pool)`.
- **What writes an observation** (Uniswap v3-core, commit `d8b1c635`): a swap that changes the tick (`UniswapV3Pool.sol:732-748`), and a mint or burn with liquidity > 0 of a position whose range contains the current tick (`_modifyPosition`, `:327` and `:336-348`). At most one per block (`Oracle.sol:90`). A swap within the tick, a mint or burn outside the range, a burn of 0, `collect` and `flash` write nothing. Confirmed per action on the fork.
- **Why that closes it.** Without an observation in the block, tick and in-range liquidity are still as they were at the start of the block. In the run's block an attacker can therefore at most push within the starting tick (≤ 1 tick ≈ 1 bp per pool) and cannot place JIT liquidity in the range. That rules out push-then-JIT from the review of PR #18 (up to +4.4 bp of the run) and pushes across the tick boundary. The starting tick is therefore also simply `slot0.tick`; the derivation from two observations, `BlockStartUnknown` and the requirement of two observations in the constructor are gone.
- **Rounding.** The price within the starting tick is not known (a swap within the tick writes nothing). The window counts from the unfavourable edge of the tick, so the rounding costs honest runs at most 1 bp of room (5–6 bp per direction) and never gives an attacker room.
- **Multiple runs in one block** share the same window, but only as long as no run changes the tick; after that the pool has been touched in that block and the next run reverts with `PoolTouchedThisBlock`.
- **Failure rate.** Measured over 2,000 blocks around block 51,390,800 (logs of both pools, sample of 80 blocks checked against `observations`): 0% of attempts fail if the transaction is at the top of the block, 4.3% halfway and 7 to 11% at the bottom. A rejected attempt costs a keeper that simulates first no gas and succeeds in a later block. Note: an `eth_call` on the latest block also sees any activity in that very block as a touch (in 363 of the 2,000 blocks there was activity in one of the two pools), so read and simulate again in a later block.
- **Residual risk: LP with a large share (review F-4).** A push within the starting tick writes no observation and is therefore invisible: that is the granularity of the tick. The victim can therefore trade up to ~1 tick (≈ 1 bp) worse per pushed pool, ~2 bp in total. An attacker who minted most of the active liquidity themselves in an earlier block gets most of the pool fee of their push there and back returned; what the push costs them is the protocol fee part of that fee. The protocol fee is a Uniswap governance setting, per pool: `feeProtocol` is currently 68 on both pools (read on chain with `slot0()` on 17 September 2026, block 51,404,889: 4 and 4, so 1/4 of the LP fee goes to Uniswap). The bounds, set by Arjan:
  - **current protocol fee: < 0.5 bp of the run.** Measured up to +0.18 bp (block 51,402,700: +0.185 EURC on a buy of 10,000 EURC, LP share 95%, `test_fork_lpAttackerProfitAtCurrentProtocolFee`). Around the window's capacity it is negative: −1.68 bp to −2.93 bp (highest value per block, see the table below).
  - **protocol fee 0: victim < 2.05 bp; the attacker's profit has no fixed bound.** The victim loses ~1 tick per pushed pool through the push, measured +1.99 bp, independent of the protocol fee (asserted). The attacker's extra profit is something other than that loss: they compare pushing with not pushing at the same correction, and if the push makes the run smaller, then as LP they also do not lose the margin on the volume that drops away. That surplus does not come from the victim, but it is profit from the push, and it depends strongly on the pool state: an LP with 99.9% of both pools gets +1.93 to +4.07 bp on a run just below capacity over five measured blocks (table below; from +1.93 to +4.07 bp within ~400 blocks). That is why `test_scenario_lpNearCapacity_protocolFeeOff_victimBelowTwoBp` only tests the victim and logs the attacker's profit (verification 579f763). Until that verification this said < 2 bp: the test then compared at an equal run and did not see the avoided loss. Protocol fee 0 is a hypothetical Uniswap governance setting (currently `feeProtocol` 68) and requires ~99.9% of the active liquidity in both pools (100 to 1,000 times the current amount). Accepted by Arjan. For smaller runs (2,000–10,000 EURC) up to +0.86 bp.
  - The outcome shifts per block with the pool state; the contract does not change for this. Making the push within the tick harmless would cost an honest run up to ~1 bp of room when the price naturally sits at the bottom of the tick.
- **Not covered: pushing at the end of the previous block** (review I-4). The block check does not see that. It is not atomic (arbitrage in between) and the spot check (layer 3) bounds it. That spot check measures against Chainlink, not against the market. If a feed lags within its deviation threshold in the attacker's favour, that lag adds to the 50 bp (self-audit 2026-09-17, L-F). Measured at block 51,425,248 (`audit/2026-09-17-self/poc/PrevBlockLagFork.t.sol`: correction 10,000 EURC, push only in EURC/USDC, no arbitrage between the blocks, cbBTC/USD 30 bp and EURC/USD 10 bp behind):
  - largest accepted push without lag 50 bp (buy) / 40 bp (sell), with lag 90 / 80 bp;
  - LP 99% at protocol fee 0: extra profit +44.2 bp without and +82.3 bp with lag (buy); the victim then trades 123.5 bp below the real price, including the fee;
  - at the current protocol fee the attacker loses 161 to 485 bp of the run on that largest push.
  - larger runs and other pools (self-audit leads 17 and 18, `audit/2026-09-17-self/poc/Leads17And18Fork.t.sol`): pushing in EURC/USDC only remains the worst case, up to +88.1 bp at a correction of 50,000 EURC. Pushing in USDC/cbBTC or in both pools costs a fixed amount of pool fee to the existing LPs of that deep pool (~300 USDC for 90 bp) and only pays off for large runs (+50.7 / +63.7 bp at 100,000 EURC). The attacker's extra profit always stays below the victim's extra loss (at most 90.6 bp). A push within the tick in the run's block adds nothing, with or without lag (victim ≤ 1.26 bp, attacker ≤ −0.08 bp). Accepted by Arjan.

  The loss bound `FEE_BPS + maxSlippageBps` therefore applies relative to the feed; relative to the market the lag comes on top (at most ~40 bp). No fix in the contract: lowering `MAX_SPOT_DEVIATION_BPS` makes honest runs revert more often.

**2. Run size from the liquidity.** `_plan` estimates how much input would bring the price to the edge of the window and uses `SIZING_BPS` (75%) of that. In doing so it uses the smallest liquidity up to that edge (review L-1): the in-range liquidity now, and beyond the next initializable tick boundary in the swap direction the liquidity after crossing (`liquidityNet` via `ticks()`). With tickSpacing 10 there is at most one such boundary per direction within the window, so a `tickBitmap` lookup is not needed. This way an owner no longer gets stuck on a position that ends just above or below the price (previously `isDue` true and `execute` a revert in every block); the run becomes smaller. If there is no liquidity beyond the boundary, there is no run. Liquidity outside the range never makes the run larger than the in-range liquidity allows; it can however remove an existing cliff (measured: a buy chunk from 562 to 742 EURC, exactly up to that boundary). On the fork of block 51,390,800 an honest chunk is 644.7 EURC for buys (boundary 1420 with `liquidityNet` 1.03e12 lies in the window; before this fix 851.4) and 781.3 EURC for sells; a larger correction proceeds in chunks.

**JIT outside the range.** In the run's block an attacker can mint a position just outside the range in the swap direction; that writes no observation. Such a position can make a chunk larger (remove a cliff), but never larger than the in-range liquidity at the start of the block allows, and yields no extra profit on a push. `test_scenario_jitOutOfRange_currentProtocolFee` and `test_scenario_jitOutOfRange_protocolFeeOff` (`test/BlockWindowReviewFork.t.sol`) assert per run that the run does not exceed that bound (computed with `RebalancerInRangeSizing`, without tick boundary) and that the extra profit is < 0.5 bp at the current protocol fee (measured ≤ −0.21 bp) and < 2 bp at protocol fee 0. This residual behaviour has been accepted by Arjan. An edge case (self-audit 2026-09-17, L-E): if the price sits exactly on a tick boundary b (after a swap that ended there), then a position with b as its boundary in the swap direction counts as outside the range for Uniswap, but the run crosses b immediately and trades against that liquidity from the first unit. Measured at block 51,425,248 (`audit/2026-09-17-self/poc/BoundaryJitFork.t.sol`, JIT 99× the active liquidity, correction 2,000 EURC): no observation; the run stays within 1 sat of the in-range upper bound; the victim gets no less per unit; the JIT position collects +3.72 bp of the run in pool fees, at the expense of the other LPs.

**3. Spot against Chainlink.** Before and after every swap, the spot of both pools (EURC/USDC `0x7279…66fb`, USDC/cbBTC `0xfbb6…43ef`) must lie within `MAX_SPOT_DEVIATION_BPS` (0.5%) of the Chainlink price; otherwise `SpotDeviatesFromOracle`. `amountOutMinimum` follows from Chainlink and `maxSlippageBps`, so the maximum loss per run relative to the Chainlink price remains `FEE_BPS + maxSlippageBps`.

**Failures due to the spot check (audit lead 4).** The spot check applies before and after the swap, and the run's own swap pushes the combined spot of both pools in the same direction (buying makes EURC cheaper and cbBTC more expensive, selling the reverse), at most ~12 bp (6 bp per pool, the block window). An honest run can therefore only get stuck on `SpotDeviatesFromOracle` after the swap if the spot was already more than ~38 bp away from Chainlink beforehand in the direction of the run; above 50 bp the owner is not due and `execute` reverts before the swap. Measured over 720 hourly blocks in the 30 days up to 16 September 2026 (blocks 50,106,403 to 51,401,322; per block `latestRoundData` of both feeds and `slot0` of both pools, same calculation as the contract): median 5.3 bp, p99 31.6 bp, more than 38 bp in 0.69% and more than 50 bp in 0.14% of the measurements, almost entirely due to the cbBTC leg (deviation threshold 0.3%). During a fast BTC move (19 August 2026, around block 50,182,045) the deviation briefly rose to 181 bp; the longest stretch above 50 bp lasted ~60 s. Such an attempt costs a keeper that simulates first no gas; the run follows as soon as the feed updates or arbitrage restores the pool. A wider tolerance would weaken the sandwich protection and has therefore not been chosen.

**Origin of the feeds (audit lead 5).** Chainlink labels both cbBTC/USD (`0x07DA…9f9D`) and EURC/USD (`0x9867…01e0`) on Base as `dex_state_price` (Reference Data Directory for Base, retrieved on 16 September 2026). According to Chainlink's methodology for DEX State Price, that is a price from end-of-block state of the DEX pools with the most volume, weighted by volume and liquidity, with an outlier filter and a time-lag filter. Which pools are included and with what weight, Chainlink does not publish. It is therefore possible that the pools that layer 3 guards are partly in the feed itself (partial circularity). Anyone who keeps such a pool shifted over multiple blocks then shifts the feed partly along with it: the spot check sees less than the real deviation, and `amountOutMinimum` follows the contaminated feed. The maximum loss per run remains `FEE_BPS + maxSlippageBps` relative to the feed, but not necessarily relative to the market. That requires a manipulation over multiple blocks against arbitrage (on the order of tens of EURC per block; see L-3 below), while a run is only a few hundred EURC because of the block window and the proceeds per run are therefore at most a few EURC. That is why no second source has been built in. Open question to the external auditor and Chainlink: which pools and weights are in both feeds, and how long must a pool stay shifted before the feed moves along? EURC/USD is also an SVR feed. The contract deliberately reads the Standard proxy `0x9867…01e0` (`script/Deploy.s.sol`) and not the SVR proxy `0x8a55…E287`, so that the delay for the MEV-Share auction does not apply. Both proxies point to the same aggregator `0x042f…8994` (`aggregator()`, read with `cast call` on 16 September 2026).

**No fixed min/max on the feeds (audit lead 6).** `_readFeed` only requires `answer > 0` and freshness, and `_quote` rejects a price of 0. An absolute lower or upper bound has deliberately been left out. The aggregators themselves enforce no meaningful ones (`minAnswer` 1 and `maxAnswer` 2^176 − 1 on `0x51cE…e718` for cbBTC/USD and `0x042f…8994` for EURC/USD, read with `cast call` on 16 September 2026). And in this immutable contract a fixed bound would permanently halt everything at a real extreme price (a EURC depeg, BTC outside the range), with `retire` and a new deploy as the only way out. The spot check is stricter: a wrong feed only leads to a trade if both pools are at the same wrong price, and then the user trades against the actual pool price.

**Blocking runs (audit L-3).** Blocking a run gains an attacker nothing, but it is possible. Measured on a Base fork of block 51,390,800 (gas) and with the gas price and prices of block 51,400,175 (base fee 0.005 gwei, the minimum on Base; 1 ETH = 2,101 EURC):
- **Touching is the cheapest route.** A `burn` of 1 liquidity from an existing position in the range (92,630 gas) or a swap that just crosses one tick (97,056 gas) writes an observation. Every run in that block then reverts with `PoolTouchedThisBlock`, and `isDue` and `dueOwners` report nothing; in the next block the owner is due again (`test_poolTouchedThisBlock_revertsAndNotDue` in `test/BlockWindow.t.sol`). Touching every block costs ~0.001 EURC per block at tip 0, **~1.8 EURC per hour**.
- **Pushing the spot away from Chainlink is expensive.** Holding more than 50 bp deviation in EURC/USDC costs ~16 EURC per block against arbitrage that restores it every block (~29,000 EURC per hour); in 20,000 measured blocks the pool at the end of a block was never further than 6.0 bp from the Aerodrome price. `test_poc_dosBySpotPush` (`test/OracleSandwich.t.sol`) shows that the owner is due again as soon as the pool is back.
- **No contract change solves it.** A TWAP in the spot check, a relaxed block check or a second route via Aerodrome leaves the touch in place for 1.8 to 3.5 EURC per hour and costs gas, bytecode or guarantees. Only **ordering** makes blocking expensive: Base orders by priority fee within a Flashblock. A keeper with a higher tip is placed before the toucher; the attacker then has to pay that tip in every block, the keeper only per attempt.

Defence in the keepers:
- **Read as if it is the next block.** An `eth_call` on the latest block sees a touch in that block as "not due"; the keeper then sends nothing, and the attacker does not even need to be ahead of the keeper. The script in `keeper/` therefore reads `isDue` and simulates `execute` with block overrides (number + 1, timestamp + 2 s). Once per run it checks with a probe whether the node applies them (`mainnet.base.org` does, checked on 16 September 2026); if not, it falls back to the latest block and logs that. The app keeper does the same in `pinheadio/bitburo` PR #149 (still open).
- **Keep trying for the whole budget.** The script retries a temporary revert in every new block, up to `RETRY_SECONDS` (default 540 s) after the start of the run, not for a few blocks; otherwise the attacker only needs to cover a predictable window.
- **Priority fee.** The script sends from its own key with an explicit tip: 0.05 gwei without an attack (in a sample of 12 blocks the median highest tip per block was 0.14 gwei, but the ordering applies per Flashblock). After a blockade, i.e. an own transaction that reverts on chain due to a temporary cause, the tip goes to at least double and at least 10% above the toucher's tip, up to 3 gwei and never above what the keeper is willing to pay per run (tip × gas ≤ reward + budget, see [Commands](#commands)). Another keeper is not a toucher: a direct `execute` does not count, and if an `Executed` for the same owner precedes the own transaction, that owner has been served (final review F-1). After a run without a blockade the tip drops again. The next attempt only comes after a random number of blocks (30 on average), so that the attacker does not know in which block to bid.
- **Costs, estimated from the measured gas.** At 3 gwei, blocking every block costs the attacker ~0.59 EURC, ~1,050 EURC per hour. The keeper then pays ~0.25 EURC per reverted attempt (40,317 gas), ~15 EURC per hour at one attempt per minute, plus ~2.6 EURC per successful run. Without an attack a run costs ~0.05 EURC at 0.05 gwei.
- **The app keeper cannot set a priority fee.** It sends via a sponsored Privy send: Privy documents no setting for fee or speed there, the bundler chooses the fee, and the paymaster pays for a reverted attempt. It also only runs every hour. Against an attacker who touches every block ahead of the app keeper, only the open script helps (or a dedicated keeper wallet in the app).

**When is L-3 resolved?** The criterion from the L-3 measurement of 16 September 2026: measured on a Base fork with the gas price and prices of that moment, and against the keeper as it runs in production,
1. an attacker who blocks all runs for an hour pays ≥ 1,000 EURC in irreversible costs for it (gas, fees to third parties, loss to arbitrage), even if they know when the keeper runs;
2. Bitburo pays ≤ 2% of that extra during such an attack (≤ 20 EURC per hour), and nothing without an attack;
3. blocking gains the attacker nothing: no sandwich profit above the bounds above;
4. the failure rate of honest runs without an attacker does not rise;
5. after the attack ends, every due owner runs within 5 minutes.

With the script in `keeper/`, every 10 minutes and with a ceiling of 3 gwei, the estimate is: 1. ~1,050 EURC per hour; 2. ~15 EURC per hour (~1.5%); 3 and 4 unchanged, because the contract does not change; 5. within ~2 minutes: the script keeps trying for the whole retry budget and resends after a blockade within at most 59 blocks, and the next run starts one minute after the end of the budget. That relies on the ordering of the Base sequencer. Within a Flashblock the higher tip goes first, but a transaction that arrives later cannot go ahead of a Flashblock that has already been built. Which ordering setting Base runs in production cannot be verified. The app keeper does not meet 1 and 5 as long as it sends via Privy and runs every hour. The threshold of 1,000 EURC per hour is a choice (~500 × the current cost of 1.8 EURC per hour).

### Large corrections in chunks

If a run is bounded by the liquidity and the correction is not yet finished, that run opens a round (`rounds(owner)`):
- **When.** The next chunk may run `CHUNK_INTERVAL` (10 minutes) after the previous run instead of after `interval`, only in the same direction.
- **Until when.** Until the deviation is within the band, or until the round's budget is used up: `maxCorrectionBps` of the value at the first run, at least `minTradeEurc`. In addition, per chunk never more than that budget of the current value (self-audit 2026-09-17, lead 11). After that `interval` applies again, counted from the last run.
- **Closing.** A run closes the round if, according to an estimate without fee, it brings the owner within the band. With the fee a small remainder sometimes stays just outside the band; that waits for `interval`. A remaining budget below `minTradeEurc` also closes the round, and a run that is bounded by balance or allowance does not open one.

Rules that keep this safe (unit tests in `test/BlockWindow.t.sol`, invariants in `RebalancerInvariantTest*`):
- **No ping-pong.** A change of direction never starts a chunk: `NothingToDo` until `interval` has passed.
- **`setParams` aborts a running round.**
- **Budget.** A round's budget is fixed at the first run. Chunks together do not exceed it, not even after a donation to the owner (audit lead 3, covered: `test_chunk_donationDoesNotGrowRoundBudget` in `test/BlockWindow.t.sol`). If the wallet shrinks during the round (a withdrawal or a price drop), the budget shrinks along with it: a chunk is never larger than `max(maxCorrectionBps × current value, minTradeEurc)` (self-audit 2026-09-17, lead 11, covered: `test_chunk_budgetShrinksWithWallet`). Such a donation can push a run across the band boundary and choose the moment, but any caller can do that for an owner who is already due, and with the block window it yields no atomic profit (the attack grids and scenarios in `test/BlockWindowFork.t.sol` and `test/BlockWindowReviewFork.t.sol`). Reversing the direction requires a donation of at least 2 × band × total, and a chunk in the other direction never starts (`test_chunk_directionChangeNeverStartsChunk`).
- **Floor per chunk.** A chunk may be smaller than `minTradeEurc` (which applies to the correction), but never smaller than `MIN_TRADE_FLOOR`. If less than that fits in this block, the owner is not due, `execute` reverts with `BlockMoveExceeded` (or earlier with `PoolTouchedThisBlock`), and the round stays open until there is room again. If that does not happen within `interval` after the last run, a new round starts after that.
- **Price brings the owner within the band.** If a price movement (not a run) brings the owner within the band between two chunks, the round is not closed on chain; that requires a write. If the owner moves outside the band again within `interval` after the last chunk in the same direction, another chunk can still follow, within the remaining budget.

Gas of `execute` on the fork (16 September 2026, same block, run of 500 EURC): buy 397k (was 370k before the block window), sell 425k (was 399k). A subsequent chunk in the same test costs ~240k (buy) and ~262k (sell), because the storage is warm by then. The block check and the cliff fix together cost ~7k extra per run (first chunk at block 51,390,800: buy 398,654 → 405,660, sell 436,590 → 443,652) and 358 bytes of runtime bytecode (16,775 → 17,133). `test_fork_buyAndSellGasCost` guards the limit of 1,000,000, so that a keeper knows what to budget.

### Keepers and failed attempts

The contract does not remember failed attempts: `lastExecutedAt` is only set on success, so an owner that reverts structurally (blacklist, too tight slippage) stays due. The keepers handle that themselves: both simulate `execute` first and keep a per-owner cool-down that doubles with each consecutive failure.

For keepers since the block window:
- **Run frequency.** Run every 10 minutes, so that chunks of a round are picked up on time. Note: if a run always starts exactly 10 minutes after the previous one, the previous chunk was a few seconds too recent and the next chunk slips one turn (in practice 10–20 minutes per chunk).
- **Temporary reverts.** `PoolTouchedThisBlock(address)` (`0x817a53db`) and `BlockMoveExceeded(address)` (`0x66356d6d`) are temporary. Retry in every subsequent block, for a fixed time budget and not for a few blocks, and do not count them as a failure for the cool-down. The same applies to a transaction that reverts on chain while a new simulation on that block succeeds (see [Blocking runs](#sandwich-protection-audit-m-1-l-3)).
- **One run per block.** After a successful run, only try the next owner in a later block. A run that changes the tick touches the pool for the rest of the block, and an `eth_call` on that block then wrongly reports the owner as not due.
- **Read the next block.** An `eth_call` on the latest block also sees activity by others in that block as a touch. Therefore read `isDue`/`dueOwners` and simulate `execute` with block overrides for the next block (number + 1, timestamp + 2 s), after a probe confirming that the node applies them. If that is not possible, read again in a later block and handle owners that only appear then.
- **Priority fee.** Send with an explicit priority fee and raise it after a blockade (audit L-3).
- **Registration spam.** Filter the registry off-chain beforehand on balance and allowance (audit lead 9, see [Keepers](#keepers)).

## Retiring the contract

> **Not yet available on the live contract.** `0xE577…2104` was deployed from commit `f8a6d49` and lacks `retire()`; this runbook only applies from the next deploy onwards. If the current contract has to be stopped today, the only way is per user: `setParams` with `active = false` and `approve(0)` on EURC and cbBTC. Only the user can do that, not the treasury.

The contract has no admin, upgrade or pause button, but it does have one one-time and irreversible kill switch: `retire()`, callable only with the `TREASURY` key. This is the answer to audit finding M-8/M-9 (old mandates that stay invisibly active after a redeploy, and the lack of an emergency stop). There is no way back and no `unretire`.

What it does: `execute` then reverts with `ContractRetired`, `isDue` returns `(false, 0)`, `dueOwners` is empty (so the keepers automatically find nothing anymore), and `setParams` only accepts `active = false`. `sweep` keeps working to collect leftover fee.

What it cannot do: move funds. The contract never holds user funds; the mandate is an ERC-20 allowance that sits with the user in the token contracts and that `retire` does not change. The only path that ever used that allowance (`execute`) is closed after `retire`.

Execute with the treasury key (simulate first with `cast call`, only then `cast send`):

```bash
cast call <address> "retire()" --rpc-url https://mainnet.base.org --from <treasury-address>
cast send <address> "retire()" --rpc-url https://mainnet.base.org --private-key <treasury-private-key>
cast call <address> "retired()(bool)" --rpc-url https://mainnet.base.org   # true
```

Then in the app: register the address as an old address (`legacy_addresses` from audit M-8), so that users can revoke their old mandate via the app. That revocation is `setParams` with `active = false` (works normally after `retire`; `active = true` reverts) and `approve(0)` on EURC and cbBTC for the old address. Neither is needed for safety — there is nothing left that can use the allowance — but they set the mandate to inactive and remove the allowance from the token state, so that the wallet reads as clean even without knowledge of `retire`.

### Keepers

The primary keeper is `bitburo:run-keeper` in the Bitburo Laravel app: it pages through the registry via `dueOwners` and triggers everyone whose turn it is. The block window, reading the next block and the retry budget are in `pinheadio/bitburo` PR #149 (still open); the app runs every hour and sends via a sponsored Privy send without a configurable priority fee (see [Blocking runs](#sandwich-protection-audit-m-1-l-3)). The script in `keeper/` is the open fallback that anyone can run without Bitburo, with their own key and priority fee.

**Registration spam (audit lead 9).** Anyone can register with `setParams`, even without balance or allowance, and the registry never shrinks. Registering an address costs ~120k gas via a factory (measured on the fork; on 16 September 2026 ≈ $0.0017, so 10,000 addresses ≈ $17). `dueOwners` skips inactive and empty owners cheaply (~13k gas per empty, active owner), but a keeper that walks the registry in fixed portions reaches real owners less often under heavy spam: the app keeper scans 500 slots per hour and with 10,000 spam addresses would see a real owner once every ~20 hours. A balance requirement in `setParams` does not help (deposit, register, withdraw) and makes "configure first, then deposit" impossible; the contract therefore does not change. The defence lies in the keepers:
- **Script in `keeper/`.** Reads the registry with `owners`, and per 100 owners in one Multicall3 `params(owner).active` and the balance and allowance of EURC and cbBTC. Only owners who can reach a run of max(`MIN_TRADE_FLOOR`, `MIN_RUN_EURC`) in at least one direction (min(balance, allowance) of EURC, or of cbBTC at `quote()`) get an `isDue`. That is a necessary condition in `_plan`, so no owner drops out that would otherwise be executed; an attacker has to hold at least 20 EURC with allowance per address (10,000 addresses ≈ 200,000 EURC) instead of $0.0017.
- **Empty spam still costs read time (final review F-2).** One portion of 100 owners takes a median of 429 ms on `mainnet.base.org`; ~126,000 empty addresses (≈ 0.08 ETH one-off) used up the whole retry budget that way, and every run started at 0 again, so nobody was executed anymore. Now: searching has its own time limit (`SEARCH_SECONDS`, default 180 s, within `RETRY_SECONDS`), the next run starts where this one stopped (`SCAN_STATE_FILE`, default `./keeper-scan.json`; after the end it continues at 0; if a run stops with found but unread candidates, at the first of those), and a node error on a portion only skips that portion. Every slot in the registry thus gets its turn within ⌈owners ÷ owners per run⌉ runs; at 180 s and 429 ms per 100 owners that is ~42,000 owners per run. `OWNERS_FILE` (optional; addresses per line, space or comma, `#` for comments) is served first every run, before the registry.
- **Measured end to end** (local anvil with mocks, 20,000 empty registrations via a factory followed by one due owner at index 20,000, `DRY_RUN=1`, `SEARCH_SECONDS=1`, `RETRY_SECONDS=60`): the previous version (commit `0844a75`, `RETRY_SECONDS=1`) reports "Retry-budget (1 s) op: 1 kandidaten niet meer gelezen" (Dutch log output of that version: "retry budget (1 s) used up: 1 candidates no longer read") every run and executes nobody. The new version reads 2,000–7,000 owners per run (0 → 2,000 → 9,000 → 16,000 → 2,500) and finds the owner in run 4; with that owner in `OWNERS_FILE`, in run 1.
- **App keeper.** Ought to serve its own users separately (its wallets are known) and only scan the rest of the registry with the rotation. That is not yet in the app.

Nothing is left of Chainlink CRE. In v1.1.0 both the workflow and the receiving surface in the contract were removed: `onReport`, `IReceiver`, `supportsInterface`, the immutables `FORWARDER` and `WORKFLOW_OWNER`, and `lastAttemptAt`. Chainlink Automation stopped in mid-2026, CRE Early Access was never granted and the path never processed a single report on mainnet. That saves 1,604 bytes of runtime bytecode and a lot of explanation. Anyone who wants it back finds everything under tag `v1.0.0`. Note: the surface is still present in every deployed contract from before v1.1.0, including `0xE577…2104`.

The script reads the registry, pre-filters it on active, balance and allowance (lead 9, see [Keepers](#keepers)), asks `isDue` for the candidates in portions of `PAGE_SIZE` (default 20, one Multicall3 per portion), skips runs below `MIN_RUN_EURC` (default 20 EURC), simulates `execute` first with `eth_call` and only then sends the transaction. An owner whose simulation or transaction fails gets a cool-down that doubles with each consecutive failure (`COOLDOWN_SECONDS`, default 3600 s, up to `COOLDOWN_MAX_SECONDS`, default 86,400 s), tracked in `COOLDOWN_FILE` (default `./keeper-cooldowns.json`; this file, `keeper-fee.json` and `keeper.lock` are in `keeper/.gitignore`). This way an owner that reverts structurally (the contract only sets `lastExecutedAt` on success) does not cost gas every run.

Against blocking runs (L-3, see [Sandwich protection](#sandwich-protection-audit-m-1-l-3)):
- **Next block.** `isDue` and the simulation use block overrides for the next block, pinned to the block that was read, if a probe at the start of the run shows that the node applies them. Otherwise the script falls back to the latest block, logs that, and reads every portion at least twice in consecutive blocks, and after that as long as new owners keep appearing (at most `BLOCK_RETRIES` + 1 times, default 4).
- **Retry budget.** A temporary revert (`PoolTouchedThisBlock`, `BlockMoveExceeded`, or an on-chain revert whose re-simulation succeeds) does not count for the cool-down: the script retries that owner in every new block, taking turns with other blocked owners, up to `RETRY_SECONDS` (default 540 s) after the start. It waits at most `BLOCK_WAIT_SECONDS` (default 30) for a new block. After an own transaction it only reads and simulates the next owner in a later block.
- **Priority fee.** Transactions go out with `GAS_LIMIT` (default 1,000,000, the limit that `test_fork_buyAndSellGasCost` guards), `maxPriorityFeePerGas` = `PRIORITY_FEE_GWEI` (default 0.05) and `maxFeePerGas` = 2 × base fee + tip. An on-chain revert counts as a blockade if a re-simulation on the state at the start of that block succeeds (or hits the block window) and a transaction before the own transaction touched a pool (Swap, Mint or Burn) that was not itself a direct `execute` on the Rebalancer; a genuine revert on that starting state gets a cool-down, a node error never does. After a blockade, at least double and at least 10% above the highest tip of those touchers, up to `MAX_PRIORITY_FEE_GWEI` (default 3); the tip is stored in `FEE_STATE_FILE` (default `./keeper-fee.json`) and applies until `FEE_HOLD_SECONDS` (default 3600) after the last blockade.
- **Competing keepers (final review F-1).** Every `execute` swaps through both pools, so another keeper that executed the same owner earlier in the block looked like a toucher: the tip rose to 3 gwei and stayed there for an hour. Now the script also reads the `Executed` logs of that block. If an `Executed` for the same owner precedes the own transaction, that owner has been served: no blockade, no new attempt, no cool-down. The tip halves (down to the base) after every own transaction without a blockade and at the end of a run without a blockade and without an own transaction; from 3 gwei to 0.05 gwei that is 6 steps.
- **Tip ceiling from the proceeds (final review F-1).** `tip × GAS_ESTIMATE ≤ TIP_REWARD_SHARE_BPS / 10,000 × reward + TIP_BUDGET_ETH`, and never above `MAX_PRIORITY_FEE_GWEI`. The tip is paid over the gas used, so `GAS_ESTIMATE` (default 500,000; measured 475,267 for a buy) and not `GAS_LIMIT`. The reward (`KEEPER_REWARD_EURC` / 2, which every run is sure to yield since the contract gives at most half the fee as reward; 0 without `REWARD_TO`) is converted to wei with Chainlink EURC/USD (the contract's feed) and ETH/USD (`FEED_ETH_USD`, default `0x7104…Bb70`, on chain "ETH / USD", 8 decimals); if a price cannot be read, only the budget counts. At 500,000 gas the reward of 0.025 EURC itself covers ~0.024 gwei; everything above that is budget, what the keeper is willing to pay per run to break a blockade. The default `TIP_BUDGET_ETH` = 0.0015 ETH keeps 3 gwei reachable, on which the L-3 criterion above rests; anyone who wants to spend less lowers the budget and accepts that an attacker blocks more cheaply. The next send only comes after uniformly 1 to 2 × `SEND_RETRY_BLOCKS` − 1 blocks (30 on average by default). Doubling reaches the ceiling from 0.05 gwei in 6 blockades and pays at most double the tip that was needed.
- **One run at a time.** `LOCK_FILE` (default `./keeper.lock`) stops a second run. The lock contains pid and start time (final review I-5): it has expired if the pid no longer exists, or if it is older than `LOCK_MAX_SECONDS` (default 900), even if the OS gave the pid to another process after a crash. The latter is safe because a run stops itself 15 s before that age; a lock of that age can therefore not belong to a living run; after the retry budget the run reads no new candidates. A transaction that is not mined within `TX_WAIT_BLOCKS` (default 15) blocks, for example because the base fee rose above `maxFeePerGas`, is replaced with the same nonce: tip and `maxFeePerGas` each 12.5% higher (a node requires 10%), and `maxFeePerGas` at least 2 × the current base fee + tip, at most `TX_REPLACEMENTS` (default 3) times and never above the tip ceiling. If that is no longer possible, the run stops with a clear message, without a cool-down (final review I-6).

Run it every 10 minutes (for example cron `*/10`); the retry budget of 540 s leaves a minute of margin before the next run.
